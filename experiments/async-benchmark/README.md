# 비동기 전환 동시성 벤치마크 (PR #125)

LLM 호출을 `OpenAI` → `AsyncOpenAI`(await)로 전환한 PR #125의 효과를 수치화한 실험.

## 배경 / 문제

PR #125 설명은 "이벤트 루프 블로킹 제거, 동시 요청 처리 확보"였다.
하지만 "블로킹 제거"가 실제로 어떤 처리량 차이를 만드는지는 모호했다.

→ 동기(블로킹) vs 비동기(await) 동시성 모델을 동일 조건으로 비교해 정량화한다.

## 방법

LLM 호출처럼 I/O 대기가 지배적인 작업을 N건 동시에 처리하는 상황을 모사:
- 동기: time.sleep으로 이벤트 루프를 막음 (요청 순차 처리)
- 비동기: asyncio.sleep으로 대기 중 양보 (요청 동시 진행)

실제 OpenAI를 호출하지 않고 동일한 I/O 지연(0.3초)으로 모사해
순수하게 '동시성 모델 차이'만 격리 측정한다. (비용 0, 재현 가능)

```bash
uv run python experiments/async-benchmark/benchmark.py
```

## 결과

요청당 I/O 지연 0.3초 기준:

| 동시 요청 | 동기 | 비동기 | 속도 향상 | 동기 처리량 | 비동기 처리량 |
|----------|------|--------|-----------|-------------|---------------|
| 10건 | 3.00s | 0.30s | 10배 | 3.3 req/s | 33.2 req/s |
| 50건 | 15.01s | 0.30s | 50배 | 3.3 req/s | 165.8 req/s |
| 100건 | 30.01s | 0.30s | 99배 | 3.3 req/s | 331.1 req/s |

### 관찰

- 동기 처리량은 동시 요청 수와 무관하게 ~3.3 req/s로 고정 — 요청이 줄 서서 순차 처리되기 때문.
- 비동기 처리량은 동시 요청이 늘수록 선형 증가 (33 → 166 → 331 req/s) — I/O 대기 중 다른 요청을 처리하므로 N건이 사실상 동시에 진행.
- 즉 "블로킹 제거"의 효과는 동시 부하가 클수록 커진다. 단일 요청에서는 차이가 없지만, 동시 100건에서 처리 시간 30s → 0.3s(약 99배)로 벌어진다.

→ PR #125의 "AsyncOpenAI 전환으로 블로킹 제거, 동시 처리 확보"라는 표현을
"동시 100건 기준 처리량 3.3 → 331 req/s, 처리 시간 99배 단축"이라는 수치로 구체화.

## 한계

- 실제 OpenAI 응답 시간은 가변적(0.3초는 근사값)이며, 네트워크·rate limit 등 외부 변수는 제외한 격리 벤치마크.
- 실제 FastAPI 엔드포인트의 종단 성능은 배포 후 locust 측정(tests/performance/)으로 보완.
- CPU 바운드 작업에는 async 이점이 적용되지 않음 — 이 실험은 I/O 바운드(LLM 호출) 한정.
