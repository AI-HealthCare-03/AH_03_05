## 1. MVP 범위 재정의

참여기업 Uponati 필수 기능을 기준으로 Sprint 2 MVP 범위를 재정의하였다.

Sprint 2 MVP는 다음 3개 기능을 최소 구현하는 것으로 정리하였다.

1. OCR 기반 의료정보 인식
2. LLM 기반 복약/생활습관 가이드 생성
3. 실시간 챗봇 최소 구현

핵심 사용자 흐름은 다음과 같다.


회원가입/로그인
→ 의료 이미지 업로드
→ OCR 텍스트 추출
→ OCR 결과 확인 및 수정
→ 약품 정보 조회
→ LLM 복약 안내 생성
→ 결과 확인
→ 챗봇 질문 입력
→ 답변 확인


Sprint 2 MVP는 기존처럼 OCR 기반 복약 가이드 생성만으로 두기보다는, 참여기업 필수요건을 충족하기 위해 실시간 챗봇 최소 구현까지 포함하는 방향으로 정리하였다.

다만 챗봇의 모든 고도화 기능을 Sprint 2에서 완성하는 것은 범위가 커질 수 있으므로, Sprint 2에서는 최소 구현만 포함하고 챗봇 고도화는 Sprint 3 확장으로 분리한다.

Sprint 2 챗봇 최소 구현 범위는 다음과 같다.

- 사용자 질문 입력
- LLM 또는 규칙 기반 답변 생성
- 최근 3~5개 메시지 맥락 반영
- 상담 세션 생성
- 상담 메시지 저장
- 특정 상담 세션 메시지 조회
- 위험 질문 감지
- 의료기관 상담 권고
- 챗봇 안전 응답 정책 적용
- 프롬프트 버전 저장

## 2. 기능 단계 분류

요구사항과 API, ERD의 범위가 섞이지 않도록 기능 단계를 네 가지로 분류하였다.

| 단계 | 설명 | 우선순위 |
|---|---|---|
| Sprint 2 필수 MVP | 참여기업 필수요건 충족을 위한 핵심 기능 | P0 |
| Sprint 2 Stretch Goal | Sprint 2 필수 MVP 구현 후 여유가 있을 때 최소 구현 또는 초안 수준으로 당겨올 기능 | P1 |
| Sprint 3 확장 | Sprint 2 MVP 이후 챗봇 고도화, RAG, 복약 관리, 챌린지, 피드백, 알림을 확장하는 기능 | P2 |
| 상용화 검토 | 실제 출시, 운영, 수익화, 병원 연동 단계에서 검토할 장기 기능 | P3 |

Sprint 2 필수 MVP는 실제 1차 MVP 구현 범위로 정의하고, Sprint 2 Stretch Goal은 필수 구현 이후 여유가 있을 때 진행할 후보 기능으로 분리하였다.

Sprint 3 확장은 1차 MVP가 동작한 이후 서비스 완성도를 높이기 위한 기능으로 정의하였다.

상용화 검토는 현재 Sprint에서 구현하지 않고, 장기 확장 가능성을 정리하기 위한 범위로 분리하였다.

## 3. ERD 분리 결정

ERD는 전체 기능을 한 장에 모두 넣으면 테이블 수가 많아지고 가독성이 떨어질 수 있어 세 개로 분리하였다.

### 3.1 Sprint 2 MVP ERD

Sprint 2 MVP ERD는 실제 1차 MVP 구현에 필요한 핵심 테이블만 포함한다.

포함 범위는 다음과 같다.

- OCR 기반 의료정보 인식
- LLM 복약/생활습관 가이드 생성
- 실시간 챗봇 최소 구현

주요 테이블은 다음과 같다.

- users
- auth_tokens
- user_consents
- user_health_profiles
- medical_records
- processing_jobs
- medications
- drug_references
- drug_caches
- api_failure_logs
- guides
- guide_items
- chat_sessions
- chat_messages

Sprint 2 MVP ERD에서는 사용자가 이미지를 업로드하고, OCR 결과를 확인 및 수정한 뒤, 약품 정보 조회와 LLM 가이드 생성을 거쳐 챗봇 질문/답변까지 이어지는 핵심 흐름을 지원한다.

### 3.2 Sprint 2 Stretch Goal + Sprint 3 확장 ERD

Sprint 2 Stretch Goal + Sprint 3 확장 ERD는 1차 MVP 이후 확장할 기능을 포함한다.

- 챗봇 고도화
- 생활습관 챌린지
- 피드백
- 알림

주요 테이블은 다음과 같다.

Sprint 3 확장 ERD는 Sprint 2에서 만든 최소 기능을 기반으로, RAG 기반 가이드 보강, 복약 관리, 챗봇 품질 개선, 챌린지, 피드백, 알림 기능을 확장하기 위한 구조이다.

## 4. API 명세서 정리 결정

API 명세서는 Notion에서 제공된 작성 기준을 반영하여 클라이언트와 서버가 어떤 데이터를 주고받을지 명확히 정의하는 문서로 정리하였다.

각 API에는 다음 항목을 포함하도록 하였다.

- Request URL
- Method
- Description
- Request Header
- Request Parameter
- Request Body
- Response Body
- Status Code
- 기능 단계
- 우선순위
- 인증 필요 여부
- 비동기 여부
- 담당자
- 협업
- 완료 상태

API 명세서는 두 가지 방식으로 확인할 수 있도록 구성하였다.

### 4.1 도메인별 시트

도메인별 시트는 백엔드 개발자가 기능 영역별로 API를 확인하기 쉽도록 구성하였다.

도메인별 분류는 다음과 같다.

- 회원/사용자
- 기록/OCR
- 약품/가이드
- 챗봇/작업상태
- Sprint3 확장
- 상용화 검토

도메인별 시트는 각 기능 영역의 API를 한 곳에서 확인할 수 있도록 하여, 담당 역할별 작업 범위를 파악하기 쉽게 만들기 위한 목적이다.

### 4.2 Sprint별 시트

Sprint별 시트는 회의나 작업 분배 시 구현 우선순위를 확인하기 쉽도록 구성하였다.

Sprint별 분류는 다음과 같다.

- Sprint2 MVP P0
- Sprint2 Stretch P1
- Sprint3 P2
- Commercial P3

Sprint별 시트는 지금 당장 구현해야 할 API와 이후 확장할 API가 섞이지 않도록 하기 위한 목적이다.

### 4.3 API 명세서 작성 기준

API URL은 `/api/v1/...` 형식으로 통일하였다.

Request Body와 Response Body는 프론트엔드가 Mock Data를 만들 수 있도록 JSON 예시 중심으로 작성하였다.

인증이 필요한 API에는 `Authorization: Bearer {access_token}` 헤더를 사용하도록 정리하였다.

OCR과 LLM 가이드 생성처럼 시간이 오래 걸릴 수 있는 API는 비동기 처리 구조로 분리하였다.

비동기 처리 흐름은 다음과 같다.

- 작업 시작 API 호출
- job_id 반환
- processing_jobs 상태 조회
- 작업 완료 후 결과 조회

챗봇 API는 참여기업 필수요건인 실시간 챗봇을 충족하기 위해 Sprint 2 MVP에 최소 구현으로 포함하였다.

챗봇 메시지 전송 API는 사용자의 질문을 받고, 최근 3~5개 메시지를 context로 반영한 뒤, LLM 또는 규칙 기반 응답을 반환하는 구조로 정리하였다.

## 5. 역할 분담 논의 예정

아직 팀원별 최종 역할 분담은 확정하지 않았다.

다만 Sprint 2 MVP 구현 범위를 기준으로 필요한 역할 영역은 다음과 같이 정리하였다.

| 역할 영역 | 담당 범위 |
|---|---|
| Backend A | 인증, 사용자, 이미지 업로드, OCR, records, processing_jobs |
| Backend B | 약품 조회, 식약처 API, LLM 가이드, 실시간 챗봇 API |
| Frontend | 로그인, 업로드, OCR 수정, 가이드 결과, 챗봇 화면 |
| AI/Infra | OCR 테스트, LLM 프롬프트, 챗봇 안전 응답, 배포 환경 |

위 역할은 확정된 담당자가 아니라, Sprint 2 MVP 구현에 필요한 업무 영역을 나눈 기준이다.

추후 팀 회의에서 각 팀원의 역량과 희망 역할을 반영하여 최종 담당자를 배정할 예정이다.

역할 분담 시 고려할 기준은 다음과 같다.

- Sprint 2 MVP 핵심 흐름을 끊기지 않게 구현할 수 있는지
- Backend, Frontend, AI/Infra 작업이 병렬로 진행될 수 있는지
- OCR, LLM, 식약처 API, 챗봇 API의 의존성을 고려했는지
- API 명세서와 ERD 기준으로 담당 범위가 명확한지

현재 기준으로는 역할을 아래 네 영역으로 나누는 방안을 검토 중이다.

### 5.1 Backend A 후보 영역

- 회원가입 / 로그인
- 사용자 정보
- 이미지 업로드
- OCR 작업 생성
- OCR 결과 저장
- processing_jobs 상태 관리

### 5.2 Backend B 후보 영역

- 약품 정보 조회
- 식약처 API 연동
- 약품 정보 저장
- LLM 복약/생활습관 가이드 생성
- 실시간 챗봇 API
- 챗봇 메시지 저장

### 5.3 Frontend 후보 영역

- 로그인 / 회원가입 화면
- 이미지 업로드 화면
- OCR 결과 확인/수정 화면
- 약품 정보 확인 화면
- 가이드 결과 화면
- 챗봇 화면
- 로딩 / 오류 UX

### 5.4 AI/Infra 후보 영역

- OCR 모델 테스트
- OCR 응답 파싱 기준 정리
- LLM 모델 후보 테스트
- 복약 가이드 프롬프트 작성
- 챗봇 프롬프트 작성
- 위험 질문 감지 기준 정리
- 의료 안전 고지 문구 작성
- 배포 환경 구성 검토
