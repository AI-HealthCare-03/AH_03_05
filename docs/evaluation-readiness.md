## 1. 기획 (1-1 ~ 1-3)

기획 문서·요구사항 정의서·화면 흐름도 기반 항목으로, 기획/총괄 담당 영역입니다.

- 1-1 문제 정의·필요성: **확인 필요** — 진료기록 기반 복약안내라는 문제 정의는 명확하나, 정량 근거(시장/사례) 문서화 여부 확인 필요
- 1-2 요구사항 분석: **확인 필요** — 기능/비기능 요구사항 구분 및 우선순위 문서 확인 필요
- 1-3 기획 문서 양식: **확인 필요** — 화면 흐름도·기능 정의·데이터 흐름 포함 여부

## 2. 설계 (2-1 ~ 2-3)

- 2-1 기술 스택: **양호** — FastAPI/Tortoise ORM/PostgreSQL/Redis/Docker. LLM은 OpenAI API. 선정 근거 문서화하면 5점
- 2-2 확장성: **양호** — 서비스/DTO/라우터 계층 분리, ai_worker 분리(잡 큐). 모듈 단위 확장 가능 구조
- 2-3 아키텍처: **양호** — apis/services/models/dtos 계층 명확, 의존성 분리됨

## 3. AI (3-1 ~ 3-4)

- 3-1 모델 성능 검증: **보강됨** — LLM API 기반이라 자체 학습 지표는 없으나, safety_filter 분류기 성능을 정량 측정(Recall 1.0/Specificity 1.0, 검증세트 23건). [PR #129]
- 3-2 비동기 처리: **양호** — LLM 호출 AsyncOpenAI 전환으로 이벤트 루프 블로킹 제거. [PR #125]
- 3-3 결과 편차 최소화: **완료** — LLM 호출 고정 seed 적용 + 재현성 검증 테스트. [PR #119]
- 3-4 피드백 반영 구조: **완료** — 수집·저장 + 집계 조회(GET /feedbacks/summary)로 개선 활용 구조. [PR #120]
- 3-5 RAG 구현: **완료** — guideline_chunks 모델 + OpenAI 임베딩 + 벡터 유사도 검색. [PR #172]

## 4. UI/UX (4-1 ~ 4-3)

FE 구현 영역 (작성: 조이레).

- 4-1 화면 흐름: **양호** — 주요 기능 3~4단계 이내 접근. Playwright E2E(TC-02~34)로 핵심 화면 흐름 자동 검증 [PR #136], 미커버 인터랙션·Maestro 모바일(스와이프 삭제·Enter 전송 등) 플로우 보강 [PR #193]
- 4-2 일관된 경험: **양호** — accessibilityRole/Label 전 화면 적용 [PR #163], 오프라인 배너·입력 검증 강화·ErrorBoundary [PR #161], FE 단위 테스트·Codecov 100% 달성 [PR #169]. E2E 작성 중 발견한 ChatList 검색 크래시(title null) 수정 [PR #193], 진료기록 목록 총 건수 표시 [PR #190]. (단 HealthProfileHistory·홈 복약달력은 BE 미구현으로 EmptyState 표시 — P2 확정 [PR #151])
- 4-3 액션 단계: **양호** — 핵심 경로 5단계 이내. OCR→약품 확인 전체 플로우는 선택 단계 포함 시 최대 7단계

## 5. API (5-1 ~ 5-5)

- 5-1 P95 Latency 3초: **배포 후 실측 예정** — 로컬 사전 검증 완료(조회 API P95 전부 130ms 이내). 실배포 환경 측정은 6/12 이후 locust 수행
- 5-2 HTTP Method 분리: **양호** — GET 22·POST 17·PATCH 9·DELETE 5·PUT 2, REST 원칙 준수
- 5-3 배포 환경 동작: **6/12 예정** — deploy.yml(EC2) 존재, 배포 특강(6/10) 후 실배포·동작 확인
- 5-4 인증/인가: **양호** — JWT access/refresh + 토큰 revoke + bcrypt + 비밀번호 정책(유사도 체크·잠금) [PR #162/#170]
- 5-5 비동기 응답속도: **양호** — async I/O + ai_worker 비동기 잡 처리. 동시성 99× 개선 입증(locust) [PR #125/#152]
